PURPOSE / SUMMARY 

The purpose of this document is to describe the instructions and criteria involved in the development of system level requirements with the Model Based Systems Engineering (MBSE) methodology. This process is used when establishing the MBSE baseline of a pre-existing system.

MBSE – Model Based Systems Engineering 

 

PROCEDURE / PROCESS 

As with all DRS MBSE processes it is assumed the executing engineer is trained in basic MBSE concepts and utilities including SysML, at least at the OCSMP Model User level, and implementation of SysML using Cameo Systems Modeler. This process focuses on developing the system level requirements and relationships comprising the Requirements Pillar of Solution Domain at the System Level as shown in Figure 1. 

 

Figure 1: DRS Meta Model Framework 

 

Within this work scope MBSE Engineers develop specific configurations of Requirements Tables, Requirements Derivation Tables, Relationship Map Diagrams, and Dependency Tables shown in Figure 2.

Requirements Derivation Tables 

Requirements Derivation Tables are a review tool to ensure total traceability between the parent specifications/documentation of the systems requirement model. A derivation diagram shall be created for each requirement type under the corresponding package as shown in Figure 12. 

 

Figure 12: Location of Requirements Derivation Diagram 

To setup the diagram set the row and column element types to “AbstractRequirement”, Dependency Criteria to “DeriveReqt”, the row scope to the system level requirement type package of choice, and the column scope to the customer requirements/documentation being traced to as shown in Figure 13. 

 

Figure 13: Requirements Derivation Table Setup 

 If correctly executed the diagram should look similar to Figure 14. 

 

Figure 14: Requirements Derivation Table Example 

The MBSE engineer shall now inspect traceability between requirements to ensure full traceability, creating the appropriate relationship where necessary. 

Relationship Map Diagrams 

The relationship map diagram is a requirements review tool which visually shows the relationships between requirements. It is used in the requirements review to understand the full traceability of a requirement. To start, a Relationship Map Diagram is created per Functional Requirement under the requirement type package as shown in Figure 15. 

 

Figure 15: Location of Relationship Map Diagram 

Next, set the relationship criteria to the values shown in Figure 16. 

 

Figure 16: Relationship Map Criteria 

Finally drag and drop the requirement for which this diagram is being made onto the context input as shown in Figure 16. 

As there are a large number of relationship maps created a generic table is used to list all of the diagrams. The generic table is created under the functional requirements package as shown in Figure 17. 

 

Figure 17: Relationship Map Generic Table Location 

The table shall be configured by setting the Element Type to Diagram and Scope to the functional requirements package under which the diagram was created as shown in Figure 18. 

 

Figure 18: Relationship Map Generic Table Setup

Figure 20: Non-Functional Requirements Criteria 

Next, setup the criteria for the verification requirements as shown in Figure 21. Note Row Scope is the verification requirements package and column scope is the functional requirements package.

Appendix B: Requirement States 

Requirement States 

NewDraft 

The requirement is a newly authored, draft requirement. 

InChange 

A previously Approved requirement is in the process of being changed, either being reworded or deleted. 

InReview 

The requirement is in the requirements peer review process. 

Rejected 

A NewDraft requirement has been rejected in the requirements peer review process for implementation in the program baseline. 

Deleted 

A previously Approved requirement has been deleted from the program baseline through a requirements peer review or change control board. 

Approved 

A requirements peer review has approved a NewDraft or InChange requirement for implementation in the program baseline. 

Allocated 

An Approved requirement has been allocated in the program baseline and is awaiting implementation in a specified future release. 

Deferred 

Implementation of an Approved requirement has been deferred to a to be determined (TBD) future program release. 

Implemented 

An Approved requirement has been implemented in a specified program release.
