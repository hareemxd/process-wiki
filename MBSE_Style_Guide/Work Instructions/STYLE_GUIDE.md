# Purpose

This Style Guide defines the structural, formatting, and stylistic conventions for authoring MBSE Work Instructions in the DRS Naval Electronics process-wiki. It is intended to be consumed by AI authors (and human reviewers) so that new Work Instructions are consistent with the existing corpus and render correctly when converted to Confluence Storage Format (`.csf`) by the upload pipeline.

A conformant Work Instruction satisfies all rules in this guide.

---

# 1. File Conventions

- **Format:** Markdown (`.md`), UTF-8 encoded.
- **Location:** `MBSE_Style_Guide/Work Instructions/` for Work Instructions.
- **Filename:** Title Case matching the document `title` field (spaces preserved). No `MBSE-WI-NNN` prefix in the filename.
- **Companion file:** A `.csf` file of the same base name is generated by the conversion pipeline. Authors edit only the `.md` source.

---

# 2. YAML Frontmatter

Every Work Instruction begins with a YAML frontmatter block delimited by `---`. The schema is:

```yaml
---
title: {Document Title}
subtitle: MBSE Work Instruction
project: MBSE Style Guide  
genre: Work Instruction
document_number: MBSE-WI-{NNN}
metamodel_domain: {Problem Domain Black Box | Problem Domain White Box | Solution Domain Black Box | Solution Domain White Box | not applicable}
metamodel_pillar: {Structure | Behavior | not applicable}
domains:  
    - Systems Engineering  
outputs:
    - {Deliverable 1}
    - {Deliverable 2}
---
```

**Rules:**
- `subtitle`, `project`, and `genre` are fixed strings.
- `document_number` follows the pattern `MBSE-WI-NNN` (3-digit zero-padded).
- `metamodel_domain` and `metamodel_pillar` use `not applicable` for foundational/process WIs (e.g., Teamwork Cloud Administrator, Peer Review). Otherwise they identify the meta model quadrant addressed.
- `domains` is a YAML list. `Systems Engineering` is always present.
- Use `outputs` (plural). The list contains the artifacts/activities produced by following the WI.

---

# 3. Document Skeleton

Every Work Instruction contains the following H1 sections in this exact order. Sections marked *conditional* are included only when the listed condition is met.

| # | Section | Condition |
|---|---|---|
| 1 | `# Purpose` | always |
| 2 | `# DRS Naval Electronics SysML Meta Model` | conditional: `metamodel_domain != "not applicable"` |
| 3 | `# Procedure` | always |
| 4 | `# Revision History` | always |
| 5 | `# References` | always |
| 6 | `# Roles and Responsibilities` | always |
| 7 | `# Terms` | always (table optional if no terms introduced) |
| 8 | `# Appendix` | always (heading required even if empty) |

# 4. Section Specifications

## 4.1 Purpose

A 1-3 sentence statement of what the WI accomplishes. No subheadings.

**Required opening phrase:**

> This Model Based Systems Engineering (MBSE) Work Instruction **[demonstrates | describes]** the procedures **[to | for]** {verb phrase}.

When applicable, add a second sentence on standards conformance:

> Adherence to this document ensures that {object} conform to DRS Naval Electronics process and quality standards.

## 4.2 DRS Naval Electronics SysML Meta Model (conditional)

Present only when the WI addresses a specific meta model quadrant.

**Required first sentence:**

> This Work Instruction addresses the **{Domain} - {Pillar}** space of the DRS Naval Electronics Meta Model; see [Figure 1](#fig-drsne-meta-model).

Follow with one paragraph describing the quadrant's perspective. End with a centered figure of the meta model using the [Figure pattern](#62-figure-pattern) and anchor `fig-drsne-meta-model`.

## 4.3 Procedure

The body of the WI. Begins with a TOC macro (see [§6.1](#61-table-of-contents-macro)), then an H2 for each major procedural phase.

**Subsection structure** (every H2/H3):
1. A 1-3 sentence introductory paragraph explaining *what* and *why*.
2. A numbered list of imperative steps, *or* further H3 subsections.

**Heading hierarchy:**
- `## H2` — major procedural phases
- `### H3` — sub-procedures within a phase
- `#### H4` — sub-sub-procedures (rare; reserve for nested element-creation steps)

## 4.4 Revision History

Required table — exact column structure:

```markdown
| Version|Revision|Date|Author|Change History|
| ---|---|---|---|---|
|conf.1| - |MM-DD-YYYY| {Initials. Last Name}| {Description of change}|
```

## 4.5 References

Required intro sentence followed by an anchored table:

```markdown
The Modeler should review [Table 1](#tab-work-instruction-inputs) to ensure they have the required process inputs for the work activities described in this MBSE Work Instruction.

<ac:structured-macro ac:name="anchor">
  <ac:parameter ac:name="">tab-work-instruction-inputs</ac:parameter>
</ac:structured-macro>

| Document | Description |
|---|---|
| MBSE-WI-{NNN} {Document Title}| {Why this WI is a prerequisite} |
```

## 4.6 Roles and Responsibilities

Required intro sentence followed by two anchored tables (definitions, then chart).

**Intro:**
> Roles and responsibilities for the MBSE Style Guide are assigned with a RACI chart. Roles are defined in [Table 2](#tab-raci-roles-definitions) and functional areas are assigned roles in [Table 3](#tab-{document-slug}-raci-chart).

**Table 1 — RACI Definitions** (always identical, anchor `tab-raci-roles-definitions`):

```markdown
| RACI Role | Definition |
|---|---|
| Responsible | Stakeholder is the owner of the document. |
| Accountable | Stakeholder depends on the document to effectively perform their job duties. |
| Consulted | Stakeholder provides input, which may or may not be optional, to the authoring of the document. |
| Informed | Stakeholder is made aware of the document. |
| Omitted | Not a stakeholder. |
```

## 4.7 Terms

A `Term | Definition` table containing only terms introduced or used non-trivially in the document. Definitions are lowercase fragments (no terminal period required), concise, and may use `synonymous with *X*` for tool-specific synonyms.

```markdown
| Term | Definition |
|---|---|
| {Term}| {definition fragment} |
```

## 4.8 Appendix

Always present as `# Appendix`. May be empty, or contain H2 supplements (e.g., `## Actors Supplement`, `## List of Permissions`).

# 5. Inline Formatting Conventions

These conventions resolve ambiguity between visually similar elements. **Strict adherence is required** so that automated tooling and downstream readers can distinguish UI actions from named model concepts.

## 5.1 UI Menu Paths

**Format:** Bold with `>>` separator (double angle bracket).

Use `>>` for *every* navigation step in a path, including the first segment when the path begins after a noun phrase.

```markdown
**File >> Save Project As**
right-click the original project **>> Lock**
**Tools >> Cameo Collaborator >> Publish**
```

**Rationale:** `>>` is pure ASCII (XML-safe), visually distinct from the single `>` used by Markdown blockquotes, and unambiguous as a navigation separator.

## 5.2 UI Buttons, Toolbar Tools, and Field Labels

**Format:** Bold (no italic).

Apply to anything the user clicks, types into, or interacts with as a UI control.

```markdown
Use the **Align** tool ![Align](../assets/MBSE/align.png) to organize elements.
Select **Publish**.
**Document Name** matches the Smart Package name.
```

## 5.3 Named Model Elements and Tool Concepts

**Format:** Bold italic (`***term***`).

Apply to named entities in the model or tool: package names, element types referred to as nouns, dialog/panel names, model property names, role names in TWC, named tables/legends.

```markdown
identify the ***Reviews*** package
Open the element ***Specification***
Create ***Directed Aggregation*** relationships
Add ***Resource Contributor*** to Modeler users
```

**Disambiguation rule:** When a term appears as part of a `>>` UI path, it is bold (part of navigation). When it appears standalone as a named entity, it is bold italic.

| Context | Format | Example |
|---|---|---|
| Part of a navigation path | Bold | `**>> Specification**` |
| Standalone reference to the named panel | Bold italic | `Open the element ***Specification***` |
| Toolbar button being clicked | Bold | `Select **Decision Node**` |
| Element type as a noun | Bold italic | `Create two ***Control Flows***` |

## 5.4 User-Entered Values

**Format:** Backticks. Distinguish placeholders from literals.

| Type | Format | Example |
|---|---|---|
| Placeholder (user substitutes) | Backticks + `{braces}` | `` `{your username}` `` |
| Literal (user types verbatim) | Plain backticks | `` `peer review` `` |
| Mixed | Backticks with `{braces}` around variable parts | `` `{YYYYMMDD} - {description}` `` |

## 5.5 Domain Terms

Terms defined in the document's `# Terms` table receive special treatment on **first prose use** only.

**First use:** italic + Markdown link to `#terms`.

```markdown
Create elements by right-clicking in the *[containment tree](#terms)*.
```

**Subsequent uses:** plain text.

```markdown
Above the containment tree, select the search icon...
```

**Terms not in the Terms table** that are italicized for emphasis (e.g., *trunk number*, *black box*, *route*) receive plain italics with no link.

## 5.6 Inline Icons

UI icons appear inline as Markdown images, immediately adjacent to the UI element they depict (no space before; sometimes a space after).

```markdown
Select the ellipses ![ellipses icon](../assets/MBSE/Ellipses.png) **>> Move Resource**.
```

**Path convention:** `../assets/MBSE/{filename}.png`. Filenames are descriptive (e.g., `align.png`, `Ellipses.png`, `decisionnode.png`).

# 6. Confluence Macros

The conversion pipeline preserves embedded XML macros. Use only the four sanctioned macros below.

## 6.1 Table of Contents Macro

Place once, immediately after `# Procedure`. Parameters are fixed:

```xml
<ac:structured-macro ac:name="toc">
  <ac:parameter ac:name="minLevel">2</ac:parameter>
  <ac:parameter ac:name="maxLevel">7</ac:parameter>
  <ac:parameter ac:name="type">list</ac:parameter>
  <ac:parameter ac:name="outline">true</ac:parameter>
</ac:structured-macro>
```

## 6.2 Figure Pattern

Figures use a four-part structure: opening rule, anchor macro, image macro, closing rule. Figures are always center-aligned.

```markdown
---

<ac:structured-macro ac:name="anchor">
  <ac:parameter ac:name="">fig-{descriptive-slug}</ac:parameter>
</ac:structured-macro>

<ac:image ac:align="center">
  <ri:attachment ri:filename="{imagefile}.png"/>
</ac:image>

---
```

## 6.3 Table Anchor Pattern

Tables that are cross-referenced from prose require a preceding anchor macro:

```markdown
<ac:structured-macro ac:name="anchor">
  <ac:parameter ac:name="">tab-{descriptive-slug}</ac:parameter>
</ac:structured-macro>

| Column 1 | Column 2 |
|---|---|
| ... | ... |
```

## 6.4 Note and Info Macros

| Macro | Purpose | Placement |
|---|---|---|
| `note` | Warning, caution, or "do not" | Before the relevant procedure or step |
| `info` | Tip, supplementary detail, or expected condition | After the relevant procedure or step |

```xml
<ac:structured-macro ac:name="note">
  <ac:rich-text-body>
    <p>{Warning text.}</p>
  </ac:rich-text-body>
</ac:structured-macro>

<ac:structured-macro ac:name="info">
  <ac:rich-text-body>
    <p>{Tip text.}</p>
  </ac:rich-text-body>
</ac:structured-macro>
```

Inline formatting (`**bold**`, `*italic*`, etc.) is permitted inside `<p>` bodies.

# 7. Anchor Naming Conventions

Anchors are kebab-case slugs with type prefixes:

| Prefix | Used for | Example |
|---|---|---|
| `fig-` | Figures | `fig-pdsc-bdd`, `fig-drsne-meta-model` |
| `tab-` | Tables | `tab-work-instruction-inputs`, `tab-raci-roles-definitions` |

Cross-references use Markdown link syntax: `[Figure N](#fig-slug)`, `[Table N](#tab-slug)`. Numbering is manual and reflects appearance order in the document.

# 8. Voice, Tense, and Style

| Rule | Description |
|---|---|
| Mood | Imperative in procedural steps ("Select...", "Right-click...", "Enter..."). |
| Person | Third person for role references ("The Modeler", "The author", "Reviewers"). |
| Tense | Present throughout. |
| Step granularity | One action per numbered step where possible. |
| Filler | None. Avoid motivational or evaluative language. |
| Comments | Explanatory paragraphs precede numbered lists; do not interrupt them. |
| Acronyms | Define on first use: "Use Case Diagram (UCD)". Subsequent uses may use the acronym alone. |
| Lettered sub-steps | `a.`, `b.`, `c.` — use only for parallel configuration items within a single step (e.g., dialog field assignments). |

# 9. Authoring Checklist

Before considering a Work Instruction complete, verify:

- [ ] YAML frontmatter is present and conforms to [§2](#2-yaml-frontmatter).
- [ ] All required H1 sections are present in the order specified by [§3](#3-document-skeleton).
- [ ] Purpose opens with the required phrase ([§4.1](#41-purpose)).
- [ ] Meta Model section is present iff `metamodel_domain != "not applicable"`.
- [ ] Procedure begins with the TOC macro ([§6.1](#61-table-of-contents-macro)).
- [ ] Every procedural subsection has a brief intro paragraph before its numbered steps.
- [ ] All UI paths use `>>` (no single `>`).
- [ ] All placeholder values use `` `{braces}` ``; literal values use plain backticks.
- [ ] Bold and bold italic are applied per [§5.2](#52-ui-buttons-toolbar-tools-and-field-labels) and [§5.3](#53-named-model-elements-and-tool-concepts).
- [ ] Domain terms in the Terms table are linked on first prose use.
- [ ] Figures use the four-part pattern with horizontal rules.
- [ ] Anchors use `fig-` / `tab-` prefixes and kebab-case.
- [ ] RACI Definitions table matches the canonical text exactly.
- [ ] RACI Chart lists the 12 functions in the canonical order.
- [ ] Revision History row is present.
- [ ] Appendix heading is present (even if section is empty).
